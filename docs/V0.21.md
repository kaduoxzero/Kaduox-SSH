# Kaduox-SSH v0.21

## Immutable release workflow dependencies

v0.21 hardens the production tag-release workflow against mutable GitHub Action references.

Every external `uses:` entry in `.github/workflows/release.yml` is pinned to a reviewed 40-character Git commit SHA. Human-readable comments retain the intended upstream version or channel next to each pin so the workflow remains maintainable without restoring mutable tags.

The pinned release actions cover checkout, Python setup, Rust toolchain installation, Rust caching, artifact upload/download, and optional GitHub provenance attestation. The exact commits were resolved from the public upstream refs when v0.21 was prepared; no SHA was inferred from memory.

## Fail-closed pin policy

`scripts/release/test_action_pins.py` enforces the release dependency boundary in both Quality's `release-policy` job and the tag-release preflight.

The policy rejects:

- mutable tags or branches such as `@v4`, `@v7`, or `@stable`;
- abbreviated commit hashes;
- an unapproved external Action, even when it is referenced by a full SHA;
- a changed full SHA for an already approved Action until the approval map is updated in the same reviewed change;
- pinned Action lines that omit the human-readable version/ref comment;
- unpinned `docker://` action references.

Repository-local actions may remain `./...` references because they are already fixed by the checked-out release commit.

This policy intentionally targets the production `release.yml` first. Ordinary CI/Quality workflow actions remain a separate hardening scope; the tag-release workflow independently reruns its pin-policy, packaging, SBOM, tag/version, and branch-reachability preflight before publication.

## Maintenance rule

Updating a release Action requires an explicit two-part diff:

1. replace the workflow's 40-character commit SHA after reviewing the upstream change;
2. update the matching approved SHA in `test_action_pins.py` while preserving a readable version/ref comment.

A release must not be tagged if the release-policy tests have not actually executed successfully. A GitHub job ending with `steps=null` is still a runner/platform allocation failure and provides no validation evidence.
