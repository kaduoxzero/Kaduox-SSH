# Kaduox-SSH v0.20

## Release-wide SPDX dependency inventory

v0.20 adds a deterministic SPDX 2.3 JSON asset to the release pipeline.

The SBOM generator is intentionally small and auditable: `scripts/release/sbom_tool.py` uses only the Python standard library and reads the committed Cargo.lock v4 graph directly. It emits stable SPDX package IDs, package URLs, Cargo checksums when present, and `DEPENDS_ON` relationships. Duplicate package identities, unresolved or ambiguous dependency references, malformed SHA-256 checksums, and output above the 8 MiB safety limit fail closed.

The release publishes one `kaduox-ssh-<version>.spdx.json` file rather than one file per platform. This is deliberate. Cargo.lock records the workspace's resolved dependency universe; it is not a target-pruned build-material graph, so producing four target-labelled copies would imply platform precision the input does not provide. The SPDX creation timestamp is derived from the tagged commit epoch to keep repeated output reproducible without using a fictitious fixed creation time.

Quality and release preflight both execute the release packaging and SBOM policy test suites.

## Release asset gate

The publish job requires exactly:

- four deterministic binary archives;
- one release-wide SPDX JSON dependency inventory.

`SHA256SUMS` covers all five release assets. A missing, duplicated, or unexpected archive/SBOM count stops publication.

## Optional GitHub provenance attestations

GitHub attestations are opt-in through the repository variable:

`KADUOX_ENABLE_GITHUB_ATTESTATIONS=true`

Normal build and SBOM-generation jobs keep `contents: read` only. The separate attestation job receives `id-token: write` and `attestations: write` only when the feature is enabled. Before signing, it verifies the complete downloaded subject set is exactly four release archives plus one SPDX file with no unexpected files.

The job creates a provenance attestation covering those five release assets. When the opt-in is enabled, any attestation failure blocks publication. When it is disabled, the attestation job is skipped and the ordinary archive/SBOM release path remains available.

v0.20 intentionally does not create an SBOM predicate binding the release-wide Cargo.lock inventory to any one platform archive. That would assert target-specific correspondence the lockfile-only inventory cannot prove. A future archive-specific SBOM attestation must first derive and validate an exact per-target build-material graph.

The repository is private. GitHub currently requires GitHub Enterprise Cloud for artifact attestations in private/internal repositories, so the workflow does not assume that capability is universally available.

## Remaining V1 release-security boundary

v0.20 closes the deterministic lockfile-SBOM policy gap and provides an explicit provenance capability, but it does not emulate native platform publisher signing. V1 still requires a production decision and credentials for Windows Authenticode and macOS Developer ID/notarization, plus real release-run validation on functioning runners. Exact target-specific SBOM attestations remain optional future work unless the V1 distribution policy requires that stronger claim.
