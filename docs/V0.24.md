# Kaduox-SSH v0.24

## Published release qualification

v0.24 adds a post-publication qualification path for the bytes users actually download from GitHub Releases. It does not reuse `target/release` or rebuild binaries during qualification.

`.github/workflows/release-qualification.yml` runs automatically for a published GitHub Release and can also be dispatched manually for an exact tag. Its four jobs match the production release targets:

- Linux x86_64;
- macOS Intel x86_64;
- macOS Apple Silicon aarch64;
- Windows x86_64 MSVC.

Each target checks out the qualification code from the release tag itself. Before any asset download, the workflow reruns `release_tool.py check --tag` against that checkout and queries GitHub Release metadata for the same tag. A tag/version mismatch or a draft Release fails closed; manual dispatch therefore cannot silently qualify an unpublished draft. After that preflight, the workflow downloads all assets attached to that exact GitHub Release and runs `scripts/release/qualification_tool.py` against the downloaded bytes.

## Fail-closed asset checks

Qualification requires exactly four target archives, one release-wide SPDX JSON file, and `SHA256SUMS`. The checksum file must contain exactly the five non-checksum assets with safe single-component names and matching SHA-256 digests.

For each target archive, qualification enforces the deterministic packaging contract before execution:

- the expected single package root and exact eight packaged files;
- no absolute, `..`, `.`, repeated-separator, nested, or backslash paths;
- no duplicate archive entries;
- no symlink, hardlink, sparse, device, FIFO, encrypted ZIP, or other unsupported member type;
- expected executable/document modes;
- bounded archive size, member count, per-file size, and total uncompressed size;
- exact manifest schema, tag, version, target, binary filenames, sizes, and SHA-256 values.

Extraction is performed file-by-file only after the complete archive member set passes validation. `extractall` is not used.

## Executable qualification

All four packaged frontends are launched from the extracted release archive with `--version`, and every output must contain the release version.

The Linux target then points the existing real OpenSSH integration suite at the extracted **published** `kssh` binary via `KSSH=<qualified package>/kssh`. This reuses the established SSH fixture coverage for direct exec, proxying, agent behavior, SFTP upload/download, privileged transfer, recursive sync, forwarding, and related transport behavior without compiling a replacement binary.

## Policy protection

The qualification workflow's external Actions are pinned to reviewed immutable commit SHAs and included in `test_action_pins.py`. `test_rust_toolchain_policy.py` explicitly requires the qualification workflow not to install a Rust toolchain or run `cargo build`, so a future change cannot silently replace published-artifact testing with a local rebuild.

`test_release_qualification_policy.py` protects the published-release/manual-tag triggers, exact four-target matrix, tag checkout, repeated tag/version metadata validation, draft-release rejection, GitHub Release download path, no-rebuild rule, and Linux published-binary OpenSSH handoff.

## Release acceptance boundary

Post-publication qualification is an acceptance/announcement gate, not a transactional rollback mechanism: GitHub has already created the Release by the time the `release.published` event runs. A failed qualification therefore means the release must not be announced or treated as qualified; maintainers should correct or withdraw the release rather than ignoring the failure.

`SHA256SUMS` and the archive manifest prove internal consistency of the published asset set; because the checksum file is downloaded from the same Release, they are not an independent publisher-identity proof. Native platform signing and, when enabled, GitHub provenance attestations remain separate trust controls.

The current GitHub-hosted runner allocation incident still blocks real execution of this workflow in the project environment. A job with no assigned runner and no steps is not qualification evidence.
