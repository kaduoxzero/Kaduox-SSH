# Kaduox-SSH v0.27 development notes

v0.27 closes the remaining release SBOM/provenance gap by replacing the release-wide `Cargo.lock` inventory with target-specific Cargo dependency/build-material graphs and by making GitHub artifact attestation a stable-release gate.

## Target-specific SPDX SBOMs

Each of the four release matrix jobs now generates exactly one SPDX 2.3 JSON document for its own target:

- `x86_64-unknown-linux-gnu`;
- `x86_64-apple-darwin`;
- `aarch64-apple-darwin`;
- `x86_64-pc-windows-msvc`.

The generator invokes the pinned release Cargo/Rust toolchain with:

```text
cargo metadata --format-version 1 --locked --filter-platform <target>
```

Cargo's filtered `resolve` graph is treated as the platform selection boundary. The graph is walked from the `kaduox-ssh-cli` workspace package. Development-only dependency edges are excluded. Normal dependency edges are represented as SPDX `DEPENDS_ON`; build dependencies are retained as build material using `BUILD_DEPENDENCY_OF`. Every target-resolved package identity must map back to exactly one committed `Cargo.lock` package record so registry checksums remain anchored to the lockfile.

The generated file is named:

```text
kaduox-ssh-<version>-<target>.spdx.json
```

Its document namespace contains both the release tag and target triple. The creation time continues to derive from the tagged commit timestamp for deterministic output.

## Published release asset contract

A v0.27 release contains eight checksummed primary assets:

- four platform archives;
- four matching target-specific SPDX documents.

`SHA256SUMS` covers all eight assets. Publication fails if any target archive or corresponding SBOM is missing, if any unexpected file is present, or if the exact four-target set changes without an explicit policy update.

Post-publication qualification validates the target SPDX contents in addition to their SHA-256 values. It checks the SPDX version, document name, namespace, release version, target marker, local Kaduox package records, and relationship references. Therefore replacing one target's SBOM with another and recomputing `SHA256SUMS` does not satisfy qualification.

## Stable-release artifact attestations

For stable tags (tags without a SemVer pre-release suffix), GitHub artifact attestation is mandatory. A stable release cannot reach the publish job when the attestation matrix is skipped or fails.

Pre-release tags may opt into the same attestation path through:

```text
KADUOX_ENABLE_GITHUB_ATTESTATIONS=true
```

For each target, the attestation matrix downloads only that target's release artifact pair and requires exactly two files before attestation:

- the release archive;
- its target-specific SPDX file.

Two immutable-SHA-pinned `actions/attest` invocations are then required:

1. a provenance attestation covering the target archive and its SBOM asset together;
2. an SBOM attestation binding that target SPDX predicate to the target archive.

The attestation job has `contents: read`, `id-token: write`, and `attestations: write`; it does not receive `contents: write`. File attestations do not use the OCI-only artifact storage-record option.

GitHub's private/internal repository support for artifact attestations depends on the account plan. v0.27 deliberately treats missing production attestation capability as a stable-release blocker rather than silently weakening the stable release channel. Pre-release builds can still omit attestations unless explicitly enabled.

## Native platform signing remains required

v0.25 already established the native signing boundary and v0.27 does not weaken it:

- stable Windows release binaries require Authenticode signing;
- stable macOS binaries require Developer ID signing and notarization;
- pre-releases may opt into native signing through the existing repository policy.

Target-specific SBOMs and GitHub attestations complement native platform signing; they do not replace publisher identity, notarization, or OS trust-chain verification.

## Validation boundary

Release/Quality policy tests now protect:

- the exact four target-specific SBOM set;
- target-pruned Cargo graph semantics and dev-only exclusion;
- published SPDX identity and relationship integrity;
- stable vs pre-release attestation gating;
- the exact two `actions/attest` calls and their immutable Action SHA;
- four-target attestation matrix membership;
- eight-entry final `SHA256SUMS` policy;
- continued native-signing policy.

Candidate promotion still requires CI, Quality, and real OpenSSH jobs to acquire runners and execute successfully. Empty-step runner-allocation failures remain infrastructure evidence, not passing validation.
